### 4A. How the team collaborated with AI throughout implementation

The shared C01 record documents a repeated cycle of discussing a concrete issue, inspecting source code or command output, applying a selected change, and returning with the result. The distinction matters: the presence of AI assistance does not mean that a feature was accepted without review. The repository contains multiple independent feature branches and integration pull requests, and the shared discussion includes unsuccessful attempts and corrections alongside successful changes.

**Planning and decomposition.** The team discussed how to transfer a larger prototype into a maintainable React/TanStack application. The work was split across shared infrastructure and feature routes, while the Git workflow preserved separate commits and branches. The implementation did not follow a strict one-person-per-role division: Lama implemented pages across customer, freelancer, and admin areas; Norah contributed pages across those same roles; Joud implemented shared components and pages across roles. This overlap explains why later integration work required checking dependencies between independently added files.

**Code integration.** AI-supported discussions covered where a function belongs, how a page consumes shared application state, and whether an existing function or component should be reused. For example, the shared `RoleLayout` implementation and the role-specific route files were separate integration responsibilities. The route files were added only after browser inspection showed that the application content rendered without the expected navigation shell.

**Verification and correction.** The team returned build logs, Vitest results, Git status output, branch comparisons, and browser screenshots to the conversation. Recommendations were adjusted when evidence contradicted earlier assumptions. An important example is the login failure: passing authentication tests initially suggested the login rules were correct, but the actual browser problem was old localStorage data. The investigation moved from credentials to state hydration rather than changing the password rules unnecessarily.

**Release management.** The team used `develop` as the integration branch and kept `main` for a stable release after testing. Pull requests were reviewed and merged incrementally. AI guidance was used to interpret Git errors and plan safe recovery, but the recorded Git operations were performed in the team's environment.

### 4B. Technical boundaries of the Phase 4 prototype

The front end uses `AppStoreProvider` to initialize state with `createSeed()`, restore any saved demo data, and persist subsequent state updates under browser-local keys. `SESSION_KEY` represents a demo session. This is appropriate to describe as a **prototype state and session mechanism**; it is not production authentication or server-enforced access control. `RoleLayout` checks the current user and redirects users to the login page or the workspace corresponding to their role. Such redirects are useful UI guards, but real authorization must also be enforced by a backend.

The seed contains example records for demonstration and tests. Those records are not represented as actual customer research, production transactions, or externally verified marketplace data. The project documentation therefore distinguishes a successful demo workflow from a deployed, security-hardened service.

### 4E. Detailed debugging case studies

**Case 1 — `vite: command not found`.** An early attempt to run the build could not locate the Vite executable. AI assistance helped distinguish a missing dependency installation from a source-code defect. After the project environment was prepared, the build ran successfully. Later `vite-tsconfig-paths` notices were warnings about native Vite path resolution, not failed builds.

**Case 2 — Audit state mismatch.** The business-logic function attempted to read `state.audit`, but the seed stored entries under `auditLog`. The team used command-line searches and source comparison to identify every relevant reference, changed the helper and administrative return objects, and performed a focused category-creation check. The result printed `PASS: Category creation and audit logging`. This fix is traceable to `58a7c6d`.

**Case 3 — Comparing overlapping business-logic implementations.** The team compared `origin/develop:src/lib/sallihha.js` with `origin/feature/norah-business-logic:src/lib/sallihha.js`. The output showed a large diff and differences in export ordering and function formatting. Rather than treating line-count differences as proof of missing functionality, the team checked exported symbols and preserved the integrated implementation pending further review. This avoided an unverified wholesale replacement of a shared module.

**Case 4 — Merge editor failure.** Git reported that it could not open `vi` while finalizing a merge. The working tree showed that conflicts were already resolved and that Git was still waiting for a merge commit. The team completed the merge with `GIT_EDITOR=true git commit --no-edit`, then checked Git status and ran tests. The problem was the editor, not a code conflict.

**Case 5 — Diverged local `develop`.** Git reported one local-only merge and three remote-only commits. The team identified the local merge commit `e7bf3ec`, created `backup/develop-before-sync`, and then aligned the local `develop` with `origin/develop`. A fresh test branch was used to integrate the admin categories route. The resulting direct diff showed only `src/routes/admin.categories.jsx`, and the build and 27 tests passed.

**Case 6 — Incorrect browser login despite passing tests.** A customer demo login returned `Incorrect email or password`, while the authentication suite passed. The initial direct Node check failed because Node did not resolve the Vite alias `@/lib`; this was a test-execution mismatch, not evidence of a login-rule failure. Inspection of `AppStore.jsx` showed that localStorage data was loaded ahead of the new seed. The browser's stored state still contained empty users. Removing only the demo data/session keys and reloading restored the current seed, and the customer login succeeded.

**Case 7 — Foundation page instead of landing page.** Visiting `/` displayed `Project foundation is ready.` Inspection of `src/routes/index.jsx` confirmed that the placeholder was still registered as the root page. Branch searches did not reveal an already merged landing page. The team integrated a landing page with Login/Signup actions and an explanation of the repair workflow. This work was recorded in `454791b`.

**Case 8 — Dashboard content without navigation.** The customer dashboard initially rendered without the expected navy sidebar or top bar. Inspection showed that `RoleLayout` existed inside `AppShell.jsx`, but the `customer.jsx` and `freelancer.jsx` parent route files were absent. Adding these files connected nested routes to the shared shell. The fix also highlighted that shared layout components and route configuration are separate responsibilities.

**Case 9 — Sidebar destinations missing from routes.** The shell referenced `/customer/history` and `/freelancer/profile`, but the corresponding route files were missing from the integrated route listing. The team added `customer.history.jsx` and `freelancer.profile.jsx` and included them in the final integration commit `85eb9e9`.

**Case 10 — Generated TanStack output in Git status.** `.tanstack/` appeared as an untracked directory after running the development tooling. The team reviewed `.gitignore` and added `.tanstack/` and `.DS_Store` exclusions in `b94a0a3`. This was a repository-hygiene change, not a change to application behavior.

### 4F. How verification evidence should be interpreted

A **successful production build** means the tested code compiled into client and SSR bundles; it does not establish that every user action works. A **passing unit test** verifies the behavior asserted in that test, not all possible states. A **browser smoke check** verifies that a particular screen or path worked under observed conditions, not the entire application. A **merged pull request** establishes that a change entered the integration branch, not that its author used AI for every line. These distinctions are reflected in the descriptions above to avoid overstating either AI contributions or team verification.

The recorded final suite contained **28 tests across three files**: 9 authentication, 18 business logic, and 1 routing. The team planned broader customer/freelancer/admin functional testing after the merge to `develop`. The `main` branch was reserved for the later stable release, so the Git comparison is not itself evidence of a final production deployment.
